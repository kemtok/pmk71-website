# ПМК-71

Сайт на Django 5.2 и SQLite: главная, каталог, новости, заявки на продукцию.

## Установка в PowerShell

Требуется Python, совместимый с Django 5.2.

~~~powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
~~~

Вставьте полученный ключ в .env вместо replace-with-generated-key.

~~~powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py restore_seed_media
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py runserver
~~~

Сайт: http://127.0.0.1:8000/  
Админка: http://127.0.0.1:8000/admin/

Миграции добавляют шесть новостей и девять товаров. restore_seed_media копирует
их фото из assets в media, не заменяя существующие файлы. Поздние загрузки
восстанавливаются из резервной копии.

## Управление

Админка: новости, продукция, заявки. У заявок есть статусы и заметки отдела продаж.
Сотрудникам нужны статус персонала и права просмотра/изменения заявок.
Права можно назначить группе.

## Проверка

~~~powershell
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py test website
~~~

## Данные

.env, db.sqlite3 и media исключены из Git. Сохраняйте резервные копии базы
и загрузок отдельно: база содержит контакты клиентов. При обновлении кода
не заменяйте рабочую базу начальной.

Для публичного размещения настройте отдельный секретный ключ, DJANGO_DEBUG=False,
домен в DJANGO_ALLOWED_HOSTS, HTTPS и обслуживание static/media.
runserver предназначен только для локальной разработки.

## Отдел продаж и уведомления

Миграция создаёт группу «Отдел продаж»: просмотр и изменение заявок без доступа
к товарам, новостям, пользователям и удалению заявок.

Создание личного аккаунта (пароль вводится локально и не отображается):

~~~powershell
.\.venv\Scripts\python.exe manage.py create_sales_user manager --email manager@example.com
~~~

Заполните в .env параметры EMAIL_HOST, EMAIL_PORT, EMAIL_HOST_USER,
EMAIL_HOST_PASSWORD (пароль приложения почтового сервиса), DEFAULT_FROM_EMAIL,
SALES_NOTIFICATION_EMAILS (адреса через запятую), SITE_URL (доступный сотрудникам адрес).
Для STARTTLS обычно используют порт 587 и EMAIL_USE_TLS=True;
для SSL — порт 465, EMAIL_USE_SSL=True и EMAIL_USE_TLS=False.
Перезапустите сервер. Без SMTP и получателей отправка отключена.
Реальные письма для проверки автоматически не отправляются.

Уведомление отправляется после сохранения новой заявки, без телефона и комментария
клиента: письмо содержит ссылку в защищённую админку. Ошибка SMTP не теряет заявку.
В админке видны время отправки и ошибка. Повторная отправка неотправленных
уведомлений (включая старые заявки):

~~~powershell
.\.venv\Scripts\python.exe manage.py send_pending_notifications
~~~

Запускайте один экземпляр команды. При сетевом обрыве после приёма письма SMTP-сервером
повторная попытка может продублировать письмо.

## Защита форм

Все формы используют один защищённый endpoint: 10 попыток в минуту и 30 в час
на IP, 5 новых заявок в час на номер телефона. При превышении возвращается
HTTP 429 и Retry-After; интерфейс сообщает время ожидания.
Скрытое поле website отсекает простых ботов. CSRF остаётся включённым.
Идентификаторы лимитов хранятся в виде HMAC, старые счётчики очищаются автоматически.
Повтор с тем же submission_id не создаёт заявку и письмо повторно.

За прокси необходимо настроить доверенную передачу реального IP на уровне
сервера: приложение использует REMOTE_ADDR и не доверяет X-Forwarded-For.
Это базовая защита; распределённый спам требует дополнительных мер.

## Резервные копии

На этом компьютере настроена задача Windows PMK71-DailyBackup: ежедневно в 20:00
по местному времени Windows, при входе пользователя в систему. Пропущенный запуск
выполняется при доступности компьютера. Задача запускает scripts/backup.py.
На новом компьютере расписание необходимо настроить заново.

Архивы и backup.log находятся в backups и исключены из Git. В архиве:
снимок SQLite через backup API, все файлы media, контрольные суммы и количества записей.
Каждый архив проходит восстановление в изолированную папку до завершения.
Автоматическое удаление старых копий не включено.

Ручное копирование:

~~~powershell
.\.venv\Scripts\python.exe manage.py backup_site
~~~

Проверка и восстановление в НОВУЮ папку:

~~~powershell
.\.venv\Scripts\python.exe manage.py restore_backup backups/ИМЯ.zip --destination restore-test
~~~

Команда не заменяет рабочие данные. Для реального восстановления остановите сайт,
сохраните текущую базу и media отдельно, замените их содержимым проверенной копии,
затем запустите сайт. Используйте совместимую версию кода и отдельный .env:
секретные настройки и исходный код не входят в архив.

SQLite копируется согласованно даже при работающем сайте. Для точного общего среза
базы и фотографий временно приостановите редактирование/загрузку файлов.
Храните дополнительную копию архивов на другом носителе с ограниченным доступом:
архивы содержат контакты и аккаунты. Копии в папке проекта не защищают от потери диска.
